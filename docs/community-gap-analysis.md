# 社区与 Steam mod 现状：我们的系统能补什么、不能补什么

> 问题（2026-11-08，用户提出）：**在现有体系下，mod 是否已经能实现很多功能？我们的 mod 系统能让玩法从社区里长出来吗？**
> 本文只回答这两个问题，不写路线图承诺。每条结论标证据等级。

## 2. 现有体系已经能做到什么

### 2.1 榜单告诉我们的（实测）

最受好评前 29（按页面顺序）：

```

```

**形态分布**：UI 重做、美术/银河生成、全面转换（Star Wars / Star Trek / Mass Effect / Stargate）、
巨构与内容扩展（Gigastructural、NSC3、More Events）、性能优化（伞の优化）、
框架/兼容层（伞の框架、泛用规则兼容）、汉化。

**没有一个榜首 mod 靠“运行时计算”取胜**。它们赢在**内容量、美术、UI、兼容性**。

### 2.2 官方 DSL 的硬边界（领域知识 + Wiki 佐证）

- **变量是 per-scope 的数值**，有精度与取整问题（Wiki `Variables` 明列
  「Number precision and rounding」与「Limitations」）；没有数组、没有 map、没有字符串处理。
- **`scripted_effects` 是宏**：展开而非调用；没有返回值、没有递归、没有局部作用域。
- **跨系统聚合**只能靠 `every_system` 一类迭代器，代价随星系数线性增长；每次遍历都是
  一次脚本求值。
- **没有跨 mod 的库**：mod 之间只能通过“约定的变量名 / flag / on_action”耦合。
- **UI 只能走游戏提供的接口**（脚本 GUI / 本地化），不能任意绘制。
- **触发/效果的组合爆炸**由作者手工维护，没有类型检查（CWTools 是外部工具）。

### 2.3 所以“能不能实现很多功能”？

**能，而且非常多。** 上面 29 个 mod 里至少 10 个是“大型内容 overhaul”，它们用纯 DSL
+ 美术 + 本地化做出了数百小时的玩法。**内容型 mod 的瓶颈是人力与美术，不是表达能力。**

## 3. 我们的系统补的是哪一块

| 能力 | 官方 DSL | 我们的运行时 JS | 社区是否需要（榜单证据） |
|---|---|---|---|
| 任意算法/数据结构 | 无 | 有（QuickJS） | 榜单上没有需求信号 |
| 全局图度量（betweenness 等） | 需自己写脚本、代价高 | 有（已实机 27 月） | 少数“地图/战略”作者可能用 |
| 跨系统聚合/全局状态机 | `every_system` 暴力 | 一趟 JS 循环 | 同上 |
| 字符串/外部数据驱动 | 无 | 有（受沙箱限制） | 未观测到 |
| 内容量（科技/建筑/事件/美术） | **强** | 不提供 | **社区主力** |
| 分发（Workshop 订阅） | **原生** | **不提供**（要注入 DLL） | **决定性** |

**结论一：我们的系统在“内容型 mod”上不提供任何优势。** 它不会让做科技树、事件链、
巨构更容易——那些是 DSL + 美术的活。

**结论二：它的优势集中在“计算型/全局型/状态机型”玩法，而这恰好不是当前榜单的主流。**
榜单说明社区的主要需求是“更多内容”，不是“更强计算”。

## 4. 真正的闸门：分发，不是能力

这是“玩法能不能从社区里长出来”的决定性因素：

- 运行时 JS 需要**注入 DLL**（`stellaris.exe` + 按 4.4.4 锚点打补丁）；
  Workshop 订阅**不能**携带并加载 DLL。
- 每个游戏补丁都要重新锚定 RVA（我们的 4.4.4 表就是证据）；作者无法自行维护。
- 多人、成就、反作弊、杀软、Mac/Linux 全部是未知或否定项。
- 存档兼容需要作者跟着我们的 loader 版本走。

⇒ **在注入形态下，它只能是“开发者预览/高级实验层”，不可能成为社区平台的默认形态。**
这一条与我们做得多好无关，是分发形态决定的。

## 5. 直接回答

**问：现有体系下 mod 是否已经可以实现很多功能？**
答：**是，绝大部分“内容型”功能都能实现**，榜单前 29 已经证明；瓶颈是人力、美术、兼容性，
不是表达力。官方 DSL 的硬边界在“计算/全局聚合/任意数据结构”，不在“内容量”。

**问：我们的 mod 系统能让玩法从社区里长出来吗？**
答：**以现在的注入形态，不能。** 不是因为能力不够，而是因为**作者做出来的东西无法被订阅**。
如果要把这个问题变成“能”，需要把产出变成**普通 mod 可分发**的形态——也就是
「构建期 TS → 官方 `.txt`」那条编译路线，而不是运行时注入。

**运行时 JS 的正确定位**（按证据）：
1. **实验层**：验证“新能力”值不值得做（图度量、AI 行为、经济模拟）；
2. **高级作者工具**：服务少数做计算型玩法的作者，他们愿意接受注入；
3. **编译路线的后端**：把 JS 的算法在**构建期**跑成 `.txt`/数据表，产物是普通 mod。

## 6. 这个结论怎么被推翻（可检验的下一步）

| 检验 | 怎么做 | 推翻条件 |
|---|---|---|
| 作者是否真的被 DSL 卡住 | 访谈榜单前 20 里的 3–5 位作者，问“最花时间的是什么/哪次被脚本卡死” | 多数回答“计算/全局逻辑”，而不是“内容量/美术” |
| 是否有“计算型玩法”的需求 | 统计 100 个热门 mod 的脚本规模与迭代器使用 | 出现大量 `every_system` 嵌套/变量模拟数组的补丁 |
| 预览包能否长出我们没设计的东西 | 发 #39 预览，观察 2–4 周 | 作者只用它复刻现有内容 ⇒ 命题失败 |
| 编译路线是否可行 | 做最小可用：TS 算法 → 生成 `.txt` 表 | 产物无法表达目标玩法 ⇒ 转回运行时 |

## 7. 边界

- Workshop 榜单是“最受好评（发布至今）”第一页，**不是订阅数排序**；页面未登录时不显示订阅数。
- 只看了榜单名字，没有逐页读描述；没有访谈作者。
- Wiki 的 `Variables` 文章自标 3.6 校验，4.4.4 可能有新增能力（未核）。
- “社区是否需要计算型玩法”目前**没有直接证据**；本文的结论是“榜单没有显示这个需求”，
  不是“社区不需要”。

## 8. 对路线图的含义（不承诺，只排序）

1. **先做可分发**：构建期 TS → 官方 DSL/数据表，产物是普通 Workshop mod。
2. **运行时 JS 保持实验层**，不往“社区平台”方向投入（分发闸门不解决，投入没有回报）。
3. **预览包的目标改一改**：不是“让作者写 JS”，而是“验证有没有人真的需要 JS 才能做的玩法”。
