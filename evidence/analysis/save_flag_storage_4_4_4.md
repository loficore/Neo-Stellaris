# Stellaris 4.4.4 — 存档里的 flag 是按**名字**存的

**日期**:2026-11-07 **授权级别**:离线(只读一份已有存档的 `gamestate`,不启动游戏、
不注入、不占用任何 shot 额度)。**计划**:`docs/superpowers/plans/2026-11-07-runtime-js-p2-1b-flags.md`
Task 0。**上游读数**:`evidence/logs/runtime_js_phase2_safety_4_4_4.log` 的「第二发」一节
(`NEO_JS_FLAG_REJECT id=82 name=neo_hub reason=no_token raw=68639`)。

本卷只回答一个问题:P2-1b 的「早发号」会把**后续**动态名字的 token id 往后推,那么存档里
已经存在的 flag 会不会因此指到别的星系?判词在 §4,推断的边界在 §5。

## 1. 方法

- 对象:`autosave_2272.07.01.sav`(C2 第二发载入的那个战役,见 `runtime_js_phase2_safety_4_4_4.log`
  的「边界」一节)。
- 存档是 zip;读其中的 `gamestate` 成员(**44,501,038 B**),在系统块里 `grep` `flags=` 行及其后续块。
- 读数**逐字照抄**本计划 Task 0 记录的样本块(§2),不改写、不重排。

## 2. 逐字读数(一个系统块的相邻两段)

```
flags=
{
    AI_hub=62808000
    AI_system_2=62808000
    precursor_1=62808000
    neo_tier1=63313440
}
variables=
{
    neo_mark=7
    neo_probe=42
    neo_score=118
}
```

左边是脚本里写的名字(`AI_hub` / `precursor_1` / `neo_tier1`),右边是 8 位数的时间戳
(游戏日期编码),不是 token id。

## 3. 对照读数

| 读数 | 值 | 说明 |
|---|---|---|
| `neo_hub` 在整份 `gamestate` 里的出现次数 | **0** | C2 两次失败的 flag 写**没有落盘**(第二发 `raw=68639` 被 host 拦在 u16 之外) |
| `neo_score` 的出现次数 | **788** | 与同期系统数一致(每个系统一条变量),说明扫描口径能覆盖全图 |
| 从游戏脚本扫到的候选 flag 名 | **410** | 官方脚本里的 `set_star_flag` / `has_star_flag` 字面量集合 |
| 其中在这份存档里出现的 | **67** | 同一批名字在 `flags=` 块里以**名字**为键 |

## 4. 判词

**flag 的 key 是名字;右边那个大数是时间戳。** 16 位 token id 只是**进程内**的键 ——
脚本解析/执行时由 `0x1D13270` 把名字换成 id,flag 容器(`系统对象 +0x5F8`,`+0x10` 是
u16 数组、`+0x1C` 是计数)里存的是 id;但**存档序列化用的是名字**。

⇒ P2-1b 的早发号让**后续**动态名字的 id 后移,**不会**把存档里已有的 flag 指到别的星系:
重开档时引擎/脚本按名字重新发号,id 在进程内重新对齐。

## 5. 边界(不能说)

- **只有一个存档**(`autosave_2272.07.01.sav`)一次扫描;没有第二个战役复现。
- **没验其他对象是否也按名字存**:变量块(`variables=`)在同一个系统块里也用名字作键,
  但这不等于事件/舰队/星球对象也是同一口径 —— 本卷没有读它们。
- **没验引擎读档时是否先发号**:「重开档时按名字重新发号」是由 §2 的键形状与
  §4 的机制推出的**推断**,不是读档路径的读数。P2-1b 的 C2 发 2(读档)才是那条读数的落点。
- 67/410 的比例只说明「能对上」,不说明 410 是全库候选(扫描只覆盖官方脚本里的字面量)。
